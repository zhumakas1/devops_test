# devops-test

Учебное HTTP API на Python и FastAPI. Выполнено в рамках тестового задания DevOps.

## Что это за приложение

Небольшой веб-сервис с тремя маршрутами. Каждый отвечает на GET-запрос
и возвращает JSON с кодом 200 OK. Приложение слушает порт 8000.

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/` | `{"message": "Hello from FastAPI"}` |
| GET | `/health` | `{"status": "ok"}` |
| GET | `/info` | `{"app": "devops-test", "version": "1.0.0", "port": 8000}` |

Маршрут `/health` — стандартная практика: по нему системы оркестрации
проверяют, что сервис жив, и перезапускают его, если он перестал отвечать.

## Стек

- Python 3.14
- FastAPI — веб-фреймворк, определяет маршруты и превращает словари в JSON
- uvicorn — ASGI-сервер, занимает порт и принимает соединения

## Как запустить локально

Клонировать репозиторий и перейти в папку проекта:

    git clone git@github.com:zhumakas1/devops_test.git
    cd devops_test

Создать и активировать виртуальное окружение:

    python3 -m venv venv
    source venv/bin/activate

Установить зависимости:

    pip install -r requirements.txt

Запустить приложение:

    uvicorn main:app --reload --port 8000

Приложение будет доступно на http://localhost:8000

## Как проверить

Через браузер — открыть http://localhost:8000, http://localhost:8000/health
и http://localhost:8000/info

Через curl:

    curl http://localhost:8000/
    curl http://localhost:8000/health
    curl -i http://localhost:8000/info

Флаг `-i` показывает заголовки и код ответа.

FastAPI автоматически генерирует интерактивную документацию по стандарту
OpenAPI — она доступна на http://localhost:8000/docs

## Как собрать и запустить через Docker

Приложение упаковано в Docker-образ — его можно запустить на любой машине
с установленным Docker, не устанавливая Python и зависимости.

### Собрать образ

    docker build -t devops-test .

Флаг `-t` задаёт имя образа, точка в конце — контекст сборки, то есть папка,
содержимое которой отправляется демону Docker.

### Запустить контейнер

    docker run -d --name devops-test -p 8000:8000 devops-test

- `-d` — запустить в фоне
- `--name` — имя контейнера
- `-p 8000:8000` — проброс порта: слева порт хоста, справа порт контейнера

Приложение будет доступно на http://localhost:8000

### Проверить

    curl http://localhost:8000/
    curl http://localhost:8000/health
    curl -i http://localhost:8000/info

Либо в браузере по тем же адресам.

Посмотреть логи контейнера:

    docker logs devops-test

Посмотреть работающие контейнеры:

    docker ps

### Остановить и удалить

    docker stop devops-test
    docker rm devops-test

### Как устроен Dockerfile

| Инструкция | Назначение |
|---|---|
| `FROM python:3.14-slim` | Базовый образ. Вариант `slim` весит ~150 МБ вместо ~1 ГБ |
| `WORKDIR /app` | Рабочая директория внутри образа |
| `COPY requirements.txt .` | Копируется отдельно и раньше кода — ради кэша слоёв |
| `RUN pip install ...` | Установка зависимостей на этапе сборки |
| `COPY . .` | Копирование исходного кода |
| `EXPOSE 8000` | Документирует порт. Наружу его открывает только флаг `-p` |
| `CMD ["uvicorn", ...]` | Команда запуска приложения |

Два решения, которые стоит пояснить отдельно.

**Порядок копирования.** `requirements.txt` копируется отдельным шагом до
остального кода. Каждая инструкция Dockerfile создаёт слой, слои кэшируются, и
изменение слоя обесценивает кэш всех слоёв ниже. Зависимости меняются редко, а
код постоянно — при таком порядке правка кода не приводит к переустановке
зависимостей.

**`--host 0.0.0.0` в команде запуска.** По умолчанию uvicorn слушает
`127.0.0.1`, а внутри контейнера этот адрес означает сам контейнер. Запросы,
пришедшие через проброшенный порт, приходят с адреса сети Docker и были бы
отвергнуты. Значение `0.0.0.0` означает «слушать на всех интерфейсах».

### `.dockerignore`

Исключает из контекста сборки `venv/`, `__pycache__/`, `*.pyc`, `.git/`.
Это уменьшает объём передаваемых демону данных, ускоряет сборку и не даёт
попасть внутрь образа истории репозитория и локальному окружению, которое всё
равно непереносимо между машинами.

## Как работает CI/CD

Сборка и публикация Docker-образа автоматизированы через GitHub Actions.
Сценарий описан в файле `.github/workflows/docker-publish.yml`.

### Что происходит при пуше

При каждом пуше в ветку `main` GitHub поднимает чистую виртуальную машину
с Ubuntu и выполняет на ней четыре шага:

1. Клонирует репозиторий на эту машину
2. Вычисляет короткий SHA коммита — первые 7 символов хеша
3. Авторизуется в GitHub Container Registry
4. Собирает Docker-образ и публикует его с двумя тегами

После выполнения машина уничтожается — поэтому результат сборки обязательно
нужно успеть отправить в реестр, иначе он пропал бы вместе с ней.

### Триггер

    on:
      push:
        branches: [main, master]

Пуш в другие ветки сценарий не запускает.

### Права и авторизация

    permissions:
      contents: read
      packages: write

Отдельный аккаунт и секреты не требуются: авторизация в реестре идёт через
встроенный `GITHUB_TOKEN`, который GitHub создаёт автоматически на время
прогона и уничтожает после. Он действует только в пределах этого репозитория.
Право `packages: write` выдаётся явно — по умолчанию его нет.

### Теги образа

Образ публикуется с двумя тегами:

| Тег | Назначение |
|---|---|
| `latest` | Последняя сборка. Метка переезжает при каждом пуше |
| Короткий SHA коммита | Закреплён за конкретным образом навсегда |

Второй тег обеспечивает прослеживаемость: по нему всегда видно, из какого
коммита собран образ, работающий в конкретной среде. Он же позволяет
откатиться на предыдущую версию, просто запустив образ с другим тегом,
без пересборки.

### Опубликованный образ

    ghcr.io/zhumakas1/devops_test:latest

Скачать и запустить:

    docker pull ghcr.io/zhumakas1/devops_test:latest
    docker run -d -p 8000:8000 ghcr.io/zhumakas1/devops_test:latest

Пакет публичный, скачивание не требует авторизации.

## Структура проекта

    devops-test/
    ├── main.py            приложение: три маршрута
    ├── requirements.txt   зависимости с зафиксированными версиями
    ├── .gitignore         что не попадает в репозиторий
    └── README.md          этот файл

Папка `venv` в репозиторий не попадает: она весит десятки мегабайт,
содержит абсолютные пути конкретной машины и полностью восстанавливается
из `requirements.txt` одной командой.

## Трудности и как решались

**Код попал в терминал вместо файла.** При первой попытке вставил содержимое
`main.py` прямо в командную строку — терминал ответил `zsh: parse error`,
а uvicorn затем не нашёл модуль `main`. Понял разницу: терминал принимает
команды, редактор — код.

**`git init` в домашней папке.** Выполнил команду, не проверив текущую
директорию, и превратил в репозиторий всю домашнюю папку. Вывод: перед
`git init` всегда проверять расположение командой `pwd`.

**Пустой `.gitignore`.** Файл был создан командой `touch`, но не заполнен,
поэтому `__pycache__` продолжал отображаться в `git status`. Заполнил
правилами — папка исчезла из отслеживаемых.
